# 검증 대상·층위

- 실제 사용 요구·흐름을 검증하는 인수·통합 테스트 선호
- 사용자 상황·행동·최종 결과를 담은 한 문장으로 테스트 이름 먼저 결정
  - 구현 용어 없이 기능의 필요성 표현, 이름의 의도를 실제 검증
- 층위는 프로덕션 조립 경로의 포함 관계로 판단
  - 상위는 이른 진입점부터 넓은 경로, 하위는 좁은 경로
  - 인수·통합·유닛으로 구분, 통합 안에도 상대적 층위 존재
- 한 사용자 전제의 연속 단계는 적은 수의 상위 케이스로 통합
  - 진입점부터 최종 결과까지 중간 관찰·부수 효과를 순서대로 단언
  - 복귀 가능한 실패·취소·대기는 발생 단계에 포함
- 차이는 조립 경로가 갈라지는 가장 낮은 층에서 한 번 검증
  - 조립·화면 전환·부수 효과 보장이 달라질 때만 상위 반복
  - 문구·표시 위치·오류 코드 차이는 명시 요구·공개 계약일 때만 검증
- 보강할 층의 기존 케이스 확장 우선
- 순수 함수의 입출력 변형은 유닛 테스트에 집중
  - 클래스보다 함수 선호
  - 클래스는 공개 계약·함수 연결 결과만 소수 검증

# 외부 경계·상태 격리

- 페이크는 작업 전부터 존재한 외부 경계 한 층에만 적용
  - 네트워크·파일·시간 등 비결정적 I/O, 브라우저·OS·네이티브 API와 공식 SDK
  - 내부 클래스·함수·훅·주입 지점은 실제 조립 유지
  - 예: fetch 사용 모듈 대신 fetch 대체 또는 msw
- 페이크만을 위한 앱 내부 대체 지점·레이어 추가 금지
- 흐름 안에서 생성하는 상태는 주입 대신 해당 단계 경유
  - 그 상태를 쓰는 코드가 검증 흐름 안에 있는지로 판별
  - 실제 사용자 조작 → 외부 응답 대체 → 흐름 밖 전제 상태 주입 순 선호
- 한 프로세스 내 병렬 실행을 고려해 cwd 등 전역 상태 의존 주의

# 인프라·실환경성

- 기존 테스트 라이브러리·더블·인프라 재사용
- 흩어진 mock/stub/spy는 공통 페이크 모듈로 통합
  - 원본 인터페이스 유지
  - 사용처에서 예상 가능한 구현 → vi.fn() 같은 유틸 순 선호
  - 시나리오 조건·의도는 테스트 안에 명시
- 공통 하니스는 관심사 밖 외부 경계 차이와 환경 준비·구동·관찰 담당
  - 콘솔 오류 등 모든 흐름에 공통인 실행 오류만 자동 단언
  - 동일 환경에서 시나리오만 변경, 부수 효과를 유지하는 내부 리팩토링에 불변
- 페이크 인프라 부재·경계 대체 곤란 시 외부 시스템 조합·스키마·런타임
  차이·위험도 확인 후 선도입 또는 유저에게 제안
- 실제 런타임·외부 의존성·배포 산출물에 가까운 테스트가 없으면 핵심 경로 스모크
  테스트 추가 시도

# Red-Green-Refactor

- 프로덕션의 사용자 관찰 동작·공개 계약·부수 효과 추가 시 적용
  - 일회성·생성 코드·설정 제외
- 의도한 실패 확인 → 최소 구현으로 통과 → 통과를 유지하며 가독성 개선 순 반복
  - Red 생략이 불가피하면 이유를 유저에게 먼저 고지
- 요구 변경은 기존 테스트 수정 우선
- 기능 삭제는 단언·케이스 추가 대신 제거
- 비기능 요구 코드는 테스트 추가 또는 코드 제거
- 리팩토링 경로를 통과하는 상위 케이스가 없으면 동작 고정 테스트부터 추가
