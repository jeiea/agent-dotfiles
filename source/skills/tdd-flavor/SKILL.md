# 선호

- 유닛보다 실제 사용 요구·흐름을 검증하는 적은 수의 핵심 인수·통합 테스트 선호
- 보장 부족 시 기존 인수·통합 케이스 확장 → 유닛 확장(유닛 테스트 섹션 조건) →
  케이스 추가
  - 확장: 트리거·입력·환경 등 조건을 요구 상황으로 바꿔 한 시나리오가 더 많은
    경로 통과
- 테스트 이름은 사용자 상황·행동·최종 결과가 드러나는 한 문장으로 먼저 결정
  - 이름 의도를 실제 검증
  - 구현 용어 없이 기능의 필요성 표현
- 케이스 단위: 한 사용자 전제(계정 종류·권한·데이터 상태)가 진입점에서 이름의
  최종 결과까지 밟는 연속 흐름
  - 중간 단계의 관찰 결과·부수 효과는 반복되더라도 순서대로 본문에서 단언
  - 후속 단계로 복귀 가능한 실패·취소·대기 우회는 그 시점의 단계로 배치
  - 재편 시 기존 단언을 새 단계에 대응시켜 누락·의도적 제거를 유저에게 보고

# 페이크 인프라와 실환경성

- 기존 테스트 라이브러리·더블·인프라 적극 재사용
- 개별 테스트에 흩어진 mock/stub/spy 대신 setupIntegration류 공통 페이크 모듈로
  통합
- 페이크는 원본과 최대한 동일 인터페이스 유지
  - 사용처에서 예상 가능한 구현 - vi.fn() 같은 유틸 활용 순 선호
  - 시나리오별 조건·의도는 테스트 안에서 드러나게 KISS
- 공통 하니스는 관심사 밖 외부 경계 차이를 흡수하며 환경 준비·구동·관찰만 담당
  - 외부 경계 한 층만 대체, 내부는 프로덕션 조립 유지
  - 모든 흐름에 공통 적용할 실행 오류 점검(콘솔 오류 등)만 하니스 관찰로 자동
    단언
  - 테스트는 동일 환경에서 시나리오만 변경, 원하는 부수 효과를 유지하는 내부
    리팩토링에 불변
- 실환경성: 실제 런타임·외부 의존성·배포 산출물과의 거리
- 페이크 인프라 부재·외부 경계 대체 곤란 시 외부 시스템 조합·스키마·런타임
  차이·위험도 확인 후 선도입 또는 유저에게 제안
- 실환경성 높은 테스트가 전무하면 핵심 경로 스모크 테스트라도 추가 시도

# 격리 규칙 (페이크 작성/사용 전 확인)

## 작성

- 페이크는 **외부 경계에만**. 외부 경계란 작업 전부터 프로덕션 런타임이 의존하던
  - 프로세스 밖 I/O: 네트워크, 파일 시스템, 시간/타이머 등 비결정적 경계
  - 외부 소유 API/SDK: 브라우저·OS API, 네이티브 브릿지, 위 I/O의 공식 SDK
- 내부 클래스/인터페이스, 훅·함수 옵션, 생성자 주입, Context Provider는 외부
  경계 아님. 실제 조립 경로 따라 외부 I/O까지 내려가 대체 지점 선정. 예: fetch
  쓰는 모듈 대신 fetch 대체 또는 msw
- 페이크만을 위한 새 앱 내부 seam 생성 금지
  - seam이 필요해 보이면 리팩토링이자 레이어 추가. 올바른 경계로 통합 테스트
    작성, 또는 유닛 테스트 섹션 조건 충족 시 유닛 허용

## 사용

- 검증 중인 흐름 안 단계가 만드는 상태(저장소·주소 등)는 주입 대신 그 단계 경유
  - 판별: 그 상태를 쓰는 코드가 흐름 안에 있는가
- 단계 도달 수단 선호 순: 실제 사용자 조작 → 외부 시스템·환경 응답 대체(제공자
  리다이렉트 등) → 흐름 밖 전제만 지속 상태(로그인 토큰 등) 주입

# 유닛 테스트

- 유닛/통합 구분: 대상 범위와 프로덕션 조립 경로 검증 여부
- 함수 입출력 검증 케이스 확대에 집중
- 아래 모두 충족 시 통합 대신 유닛 확장으로 통합 비용 절감
  - 통합 테스트 대표 케이스 1개 이상이 A→B 호출 경로 경유
  - B는 외부 의존 없는 순수 함수
  - B의 입출력 변형이 검증 대상
- 클래스는 셋업(내부 상태·콜백·시간 제어·비동기 대기)이 복잡해지기 쉬움
  - 가능하면 함수 선호, 클래스 코드 최소화해 조립 경로만 검증
  - 클래스 테스트는 내부 함수 세부 규칙보다 공개 계약·함수 연결 결과만 소수 검증

# 고립

- 한 프로세스 내 병렬 실행 고려. cwd 등 전역 상태 의존 주의

# Red-Green-Refactor

일회성·생성 코드·설정 제외, 프로덕션 코드의 사용자 관찰 가능 동작·공개 계약·부수
효과 추가 시 적용

Red(test): 테스트의 의도한 실패 확인 → Green(feat): 최소 구현으로 통과 →
Refactor(refactor): 통과 유지하며 가독성 개선 → 다른 Red로 반복

- 요구 변경 시 추가보다 기존 테스트 수정, 기능 부재는 고정하지 않음
- 비기능 요구 코드는 테스트 추가 또는 코드 제거
- 리팩토링 대상 실행 경로를 보장하는 상위 테스트가 없으면 현재 동작 고정 테스트
  추가 후 대상 코드·테스트 수정
- Red 생략 결정 시 불가피한 이유를 유저에게 먼저 알림
